## 1. Source findings and scope of enumeration

Inventory covers all explicit production consumer constructors, scheduler entry points and boot sweeps found by searching `api` for interval/timeout, worker construction, scheduler/runner startup and sweep calls, then tracing queue callbacks, route triggers and deployment scripts. Request-driven external-effect families are separately enumerated so moving timers cannot be mistaken for global execution containment. Timer-based network deadlines, OAuth development cache expiry and per-render claim heartbeats are distinguished from independent scheduled business jobs. This is a static inventory of the frozen checkout, not proof that every indirect SDK call has a production H gate. Dependency internals, actual Azure pipeline configuration and deployed service definitions are not available; those remain explicit coverage gates.

Two A02 statements need precision: BullMQ module variables are **stored worker handles, not singleton construction guards**. `createPublishingWorker` and `createContentGenerationWorker` construct a new Worker on every call and overwrite the handle; repeated calls within one process could leave earlier workers outside the stored close path. Also current health queries are not purely observational: `health.getSystemHealth` writes a critical alert when the API-local publishing handle is absent, and `getQueueHealth` can write a backlog alert. Corrected A02 wording does not change either implementation.

`scripts/deployment/start-runtime.ps1` starts API, then standalone worker when Redis is configured, and saves PM2 state. `rollback.ps1` restarts both when a worker bundle exists. Neither resolves boot's embedded startup. Their health test accepts HTTP 200 without checking degraded JSON. The startup script's no-Redis fallback note is inconsistent with production `env.ts`, which requires Redis. `verify-release.ps1` assumes an old branch, Node 20 and 27 migrations; Linux deploy scripts describe Node 20/PM2/systemd/Nginx and are not approved Windows production provisioning. These scripts were read, never executed, even in dry-run mode.

## 4. Proposed topology and exact role-selection requirements

Target: one supervised API process on loopback 3001; one separately supervised queue-worker process initially hosting P01 and P02; one separately supervised singleton scheduler/recovery process owning P04-P10. Keeping both queue types in one worker process avoids claiming the existing entry can launch them independently. Splitting into two worker services or replicas needs an approved role selector and a new concurrency/resource budget. The scheduler/recovery process has **no implemented entry point** in the inspected build; moving those jobs is an unassigned application change, not a provisioned Windows service. API remains an authenticated enqueue/control interface and must not import-start consumers, business timers or sweeps.

Initial deployment posture: no background effects until explicit roles, dependencies and safety gates pass. Production must not default to the old embedded mode because an option is absent. Development compatibility can be retained separately under reviewed behavior; no environment variable name or executable configuration is introduced here.

Required application semantics (C01-C10 inventory below):

1. Parse trusted, versioned process-role configuration before any effectful module initialization. Distinguish HTTP server, queue-consumer roles, scheduler jobs and recovery sweeps; missing/unknown/conflicting production roles fail closed. Specify one role owner in the release manifest. Operators, queue payloads and models cannot mint role/execution authority.
2. Remove unconditional embedded production P01/P02 starts from API composition when standalone ownership is selected. Do not change `production && Redis` into an `else` that launches P03. Standalone worker validates its declared role, release, identity and dependencies before constructing consumers; accidental repeated construction must be rejected or return a proven same owner without creating another Worker. Preserve every constructed handle for drain/close.
3. Move P04-P10 to explicit scheduler/recovery composition with independent per-job admission and durable ownership where needed. Queue-worker disablement must not silently disable credit renewal, rejection enforcement, safety observation or required recovery. Conversely those controls must not bypass suspension to send. If recovery cannot be safely separated from dispatch, keep it disabled and report the resulting operational gap rather than pretending safety coverage exists.
4. Preserve P12 lease/claim renewals, authoritative receipts, error accounting, redaction, governance registration and bounded deadlines. Removing API boot side effects must not remove canonical strategic-governance binding or approved route validation. Do not replace business authorization with a role flag.
5. Bind direct E01-E09 effect boundaries as well as background execution to appropriate current authority/stop posture. API-only does not mean effect-free because routes still exist. Gate normal traffic and provider egress during staging until coverage is reviewed; do not assume `LIVE_EXECUTION=False` suppresses every historical transport.

Unsafe-to-implement-now reasons: missing approved application implementer, absent scheduler entry/build target, no role-selector code or construction guards, side-effecting/local-worker health checks, uncontrolled boot sweeps, incomplete legacy effect coverage, unmerged C/D/H composition, unresolved process/DB identities, supervisor choice and real-MySQL evidence. A can specify platform roles but cannot repair these by environment or PM2 settings alone.

## 5. Lifecycle and safety contract

States are proposed process states, separate from job results and H's operational-state vocabulary: STOPPED, STARTING, READY, DRAINING, SUSPENDED, STOPPING and FAILED. Observation remains possible in a stopped-dispatch posture. No process state proves mission success.

| Phase | Required behavior / acceptance boundary |
|---|---|
| Startup | Validate fixed role/identity/release/schema, secrets, private DB/Redis, dependency compatibility and independent stop reader before claims, schedules or sweeps. No migrations or provider probes. Registration and heartbeat writes are explicit control-plane operations, not health reads. Start in zero-dispatch posture; missing health/authority/binding denies |
| Readiness | API readiness means intended HTTP/DB/queue-producer function available, independent of an in-process worker. Worker readiness means authentic registered instance, correct release/contracts, dependencies and durable claim capability. Scheduler readiness is per configured job plus its owner/lease/last pass; disabled-by-policy is explicit, not fake healthy execution |
| Heartbeat | Owned role publishes instance nonce/release, heartbeat time, active count and drain state through authenticated control-plane writes. Preserve C's configured liveness semantics (default late 15s/stale 60s/dead 300s) when composed; platform thresholds must not invent authority. Expired C worker registers a new instance; API listener uptime is not worker heartbeat |
| Admission | Independently check execution suspension, scheduler/worker pause and emergency stop before every new claim/pass; recheck fresh R9-D/F and D/H authority before reservation/transport. Missing or stale collector/backup evidence follows H fail-closed policy. Enqueue policy is distinct from permission to consume |
| Drain | Stop local intake and new scheduled admissions, cancel future ticks and track all already-entered async claims/passes/requests. C drain blocks subsequent local claims but entered claims may finish fencing; they must recheck eligibility before dispatch. A returned stop-timer status or queue pause is not proof of zero active work |
| Suspension | Worker/scheduler/capability/mission/provider suspension blocks the relevant new effects. Preserve safe read/observation and reviewed reconciliation without sending; P10 can send and is not automatically safe. No automatic resume after health recovery, restart, lease expiry or pipeline execution |
| Planned restart/release | Independent stop or authorized drain first; wait for bounded completion, record active/uncertain work, close old resources, verify compatible manifest/schema, then register new instance. No overlap of uncontrolled scheduler owners or accidental mixed releases; restart never restores business authority |
| Crash recovery | Before durable dispatch barrier, exact claim may be reconciled under fresh authority; after barrier or ambiguous provider settlement preserve UNCERTAIN/pending, use durable receipts and R9-E/F review, never blind replay. C fixed job lease is 60s, not heartbeat-renewed; do not infer permission after expiry. Legacy BullMQ attempts are not new authorization |
| Shutdown | Invoke every timer stop and drain all in-flight passes; close every consumer, producer and Redis client (both Redis and ioredis), DB resources and render child processes. Worker currently handles SIGINT/SIGTERM and BullMQ close only; API lacks coordinated equivalent. Windows SCM/wrapper delivery and stop deadline require an actual drill. Forced termination preserves uncertainty and evidence |
| Emergency stop | Independent, runtime-unwritable control plus H latch; missing reader means stopped. Apply at admission and after async evidence loading/immediately before effect, including API direct paths. In-flight external effects cannot be recalled. Retain evidence and human reconciliation; explicit independent administration needed for restoration |

Platform service stop/start permissions, backoff, maximum restart rate, shutdown timeout, scratch/CPU/memory/concurrency budgets and designated operator remain D02/D05/D11/D12 choices. Never invent production timing guarantees from offline fixtures.

## 6. Read-only, role-aware health specification

| Health surface | Required read-only semantics | Current gap |
|---|---|---|
| API liveness | Listener/event loop/process identity only; bounded response with no DB/Redis/model/SMTP/provider checks | Current general health mixes dependencies/worker checks; proposed separate route has no approved name or implementation |
| API readiness | Bounded DB SELECT, Redis PING/producer connectivity and current compatible release/config status; sanitized failures; no query creates queues, workers, registrations, alerts or business rows | `getSystemHealth` checks API-local publishing handle and can createAlert; absent Redis reported OK in dev; HTTP 200 may contain degraded state |
| Worker health | Observer reads actual worker instance/heartbeat/release/drain/active counts from trusted durable evidence; both queue roles observed; missing/stale becomes UNKNOWN/unavailable | API-local handle presence is not standalone worker evidence; not evidence that content worker is alive; no validated production heartbeat binding |
| Scheduler health | Per-job owner, enabled policy, last start/completion/status, in-flight age, next due and lease observation where available; stopped future ticks distinguished from active pass | Local lifecycle/metrics/listening getters expose partial snapshots only; credit renewal lacks full lifecycle/status; getters cannot register/start missing owners |
| Alert pipeline | E collector/classifier emits alerts separately from health query; independent channel monitors silence and delivery failures | `getQueueHealth` creates backlog alert; Redis client connect/error handlers create/resolve alerts. Probe initialization must not trigger hidden write callbacks |

Health collection must not import `boot.ts` to create an app or inspect its timers: import itself starts work. Use side-effect-free app/status modules after approved refactor. SELECT/PING clients used for probing must not lazy-create business queues or attach write-producing error handlers. Health reads must not reconcile, send, renew a lease, mutate H policy or clear kill/safe-mode state. E's UNKNOWN/dedup/tenant isolation and secret minimization apply. Separate health from control mutations with authentication and least-privilege observer access; public output never reveals raw exception/connection material. Startup/rollback tools must parse the typed readiness verdict and expected release/role, not merely HTTP 200. All proposed health changes remain unimplemented.

## 9. Open decisions and traceability

M3 explicitly broadens local A03 beyond A01's release/storage label to this process-ownership specification; it does not renumber A01-A16 or implement later requirements. Safe implementation is blocked until explicit application owner approval and coordinated C/D/H/legacy effect review; documentation can be accepted while these gates remain open. No application code, deployment configuration, service, provider or autonomy was changed. Stop after A03; do not begin A04.
