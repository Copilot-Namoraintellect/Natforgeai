# WBS-R3.1 — GAP18 Reservation Wiring Evidence Note

**Branch:** `recovery/r3-integrity-closure`
**Status:** evidence gathered pre-implementation, per R3.1 mandate.

## Evidence note

```
GAP18_ROOT_CAUSE=
  The governed credit-reservation authority is complete library code with no
  production caller. The engine header states the scope explicitly:
  "this slice establishes the authority only. Existing billing callers are
  migrated in later slices" (api/lib/billing/credit-reservation-engine.ts:18-21).
  Import grep for credit-reservation* outside api/lib/billing/: zero non-test
  importers. The real forward execution path (runAgent,
  api/lib/agents/runner.ts:92-106) still performs an unreserved up-front
  deductCredits plus a best-effort adminAdjustCredits refund on provider/schema
  failure (:205-218). The later migration slice was lost with WBS20/WBS21 and
  is reconstructed here.

GAP18_EXPECTED_AUTHORITY=
  reserveWalletCredits (wallet row lock -> durable hold -> capacity check)
  -> settleWalletCredits (guarded CAS settle + deterministic-keyed deduction
  via deductCredits) on chargeable completion;
  releaseWalletCredits (reserved -> released, no wallet mutation) on the
  existing refund classes. All transitions already defined by the WBS8A
  contract; no new semantics invented.

GAP18_BYPASS_PATH=
  triggers.ts mints the caller-stable billing identity (R1.3,
  buildAudienceBillingIdentity :219 / buildDistributionBillingIdentity :256)
  -> audience-agent.ts:267 / distribution-agent.ts:93 forward it as
  billingIdempotencyKey -> runner.ts:99-106 keyed deductCredits at start,
  keyed refund never applied (refund path is unkeyed adminAdjustCredits
  :205-218). Reservations are never consulted anywhere on this path.

GAP18_SAFE_FIX_BOUNDARY=
  Migrate ONLY the keyed runAgent path (billingIdempotencyKey present) to
  hold -> settle/release. Outcome-class net balances mirror the accepted
  legacy semantics exactly:
    - success                        -> settle (charge, exactly once)
    - provider/schema failure        -> release (no charge)
    - any other failure              -> settle (charge retained)
  The legacy unkeyed path (image router, manual runs, creative post-success
  keyed deduction, strategy-run charge) is untouched. Success-path settle
  failure propagates (fail closed; the hold stays 'reserved' and is
  recovered by the idempotent retry below). Failure-path reconciliation is
  best-effort + logged, matching the existing refund convention.
  Retry/exact-once: reservation identity, settle and release keys are pure
  functions of the caller-stable billing identity, so a re-dispatched step
  replays the same reservation and drives it terminal at most once.
  Stale-hold policy (existing repository policy, no expiry invented): a
  crash-window 'reserved' hold is recovered when the same logical step is
  retried — reserveWalletCredits returns the committed hold as an
  idempotent replay and the rerun settles/releases it.
  No schema, migration, or wallet-mutation semantic change: settlement
  still deducts through the accepted deductCredits ledger path.
```
