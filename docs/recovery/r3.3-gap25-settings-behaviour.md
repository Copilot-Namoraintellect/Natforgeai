# WBS-R3.3 — GAP25 Settings Behaviour Report

**Branch:** `recovery/r3-integrity-closure`
**Status:** CLOSED (one security-adjacent defect fixed; two surfaces verified honestly non-semantic)

## R1.7 findings re-examined against repository evidence

### 1. Integration tokens exposed to the client — FIXED

`integration.getConnectedPlatforms` selected
`socialIntegrations.pageAccessTokenEncrypted` and serialized it to every
authenticated client (flagged by the R1.7 audit; contradicted AGENTS.md §13
"Tokens are never exposed in the UI").

Evidence from the consumer side: the only frontend use
(`src/lib/content-studio/logic.ts` `getInstagramReadinessError`,
`src/pages/ContentStudio.tsx` mapping) was a **truthiness presence check**
backing the "reconnect Meta" readiness message — the ciphertext value itself
was never used.

Fix (narrowest, behaviour-preserving):
- `api/integration-router.ts`: the encrypted token no longer leaves the API;
  the payload carries `hasPageAccessToken: boolean` derived server-side.
- `src/lib/content-studio/logic.ts`: `ConnectedIntegrationLike` carries
  `hasPageAccessToken?: boolean`; readiness check unchanged in behaviour.
- `src/pages/ContentStudio.tsx`: maps the new field.
- `api/integration-router.test.ts` (new): asserts the ciphertext appears
  nowhere in the serialized payload and the presence signal tracks the stored
  token.

AGENTS.md §13 now holds true against the code — no documentation change
required (the code was corrected to the documented contract, the preferred
resolution of the R1.7 contradiction).

### 2. Notifications tab — verified honestly labelled, no action

`src/pages/Settings.tsx` Notifications renders three static "Coming Soon"
badges. Repository sweep: no notification preference is persisted anywhere
(zero `notification*` matches in `api/**` outside test mocks), nothing is
settable, and the surface explicitly disclaims availability. It is not a
decorative *setting* — no setting exists to be misleading. Wiring real
notifications would be inventing product behaviour (no authoritative consumer
exists in the repository); removing an honestly-labelled placeholder is
product churn without evidence. Documented as intentionally deferred.

### 3. `getPlatformConfigStatus` — reclassified: real reporting, not decorative

Returns `{ metaConfigured, linkedinConfigured }` from env presence. It has
live consumers (Onboarding, Settings, Integrations, ContentStudio render
configured-state badges from it) and the actual gating enforcement is
server-side at `initiateConnection` (`NOT_CONFIGURED` when env is absent), so
the surface cannot mislead a user into a broken OAuth flow. Read-only
reporting of real configuration — retained.

## Verdict

Every settings surface now either materially affects an execution path
(integrations connected-gate, approvalMode, autoPublish, 2FA — verified in
R1.7), is honest read-only reporting (`getPlatformConfigStatus`), is an
explicitly labelled future placeholder (notifications), or no longer leaks
secrets (`getConnectedPlatforms`). Where a setting was retained, existing
tests prove the execution-path effect; the new token-boundary test proves the
corrected contract.
