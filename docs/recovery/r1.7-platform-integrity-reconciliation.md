## GAP18 — Reservation unwired → STILL OPEN

The credit-reservation machinery is complete library code but has no production caller:

- `createCreditReservation` / `reserveCredits` / `buildCreditReservationId` / settle / release live in `api/lib/billing/credit-reservation.ts` (:253, :355, :396), `credit-reservation-store.ts`, `credit-reservation-engine.ts`.
- Import grep for `credit-reservation*` outside `api/lib/billing/`: **zero non-test importers**. Every call site is inside `credit-reservation.test.ts`, `credit-reservation-store.test.ts`, `credit-reservation-engine.test.ts`.
- The registry is in-memory (`credit-reservation.ts:356-357`) — built as a library awaiting a caller.
- Production billing bypasses reservations entirely and idempotently deducts via `creditTransactions` (e.g. `api/lib/workflow/triggers.ts:462-469`, key `creative-success:{campaignId}:approval:{approvalId}`); WBS-R1.3 added caller-stable billing identities on the same ledger for the audience/distribution chain.

**Reconciliation note:** forward-path billing protection is currently provided by keyed `deductCredits` claims + billing identities. Wiring the reservation engine (hold-then-settle) would change billing semantics of accepted flows; that is a deliberate product decision, not reconstructed here.

## GAP24 — Scheduling disjoint → STILL OPEN

Two scheduling systems exist with no bridge:

- `schedules` table (`db/schema.ts:443`) is consumed **only** by `api/schedule-router.ts` (reads :24, :47; insert :101; update :144; delete :155). Nothing else reads or writes it.
- `publishing_queue` rows are created by three writers, none touching `schedules`: `api/lib/agents/distribution-agent.ts:139-151` (own schedule output), `api/content-router.ts:1739, 1841, 1879` (`publishCampaignPack`), `api/publishing-router.ts:75` (`schedulePosts`).
- The Calendar UI papers over the split by querying both side-by-side (`src/pages/Calendar.tsx:44,47,49`); `schedule.create` writes only the `schedules` table.

**Consequence:** a calendar schedule is a display record with no execution path. Convergence (calendar → queue enqueue) is a feature decision for a future slice; not invented here.

## GAP29 — Launch/package/queue edges → PARTIALLY WIRED

Verified call graph:
1. Distribution complete → `campaign_launch` request + lineage (`triggers.ts:266-291`).
2. Decision: ownership-scoped lookup (`approval-router.ts:692-695`), in-tx audit (:721-742), post-commit async `onApprovalResolved` (:766-775).
3. Approved → `approve_launch` → `enqueueApprovedPublishingRows` (`triggers.ts:355-365`, :295-338) → deterministic BullMQ jobId (`api/lib/queue/bullmq.ts:106-129`).
4. Package path: single production caller `api/content-router.ts:1802`; persisted atomically with the approved row (:1879-1890) and executed via `publishSinglePost` (:1915).
5. Execution: BullMQ worker → `publishSinglePost`; 60s fallback runner (`publishing-runner.ts:1492-1515`, :1451, :1438-1448).
6. Readiness/duplicate defence: `validatePrePublishReadiness` (:931) fails closed (:984-988); deterministic jobId prevents duplicate enqueue.

**Discontinuities found (reported, not fixed):**
- **(a) Rejected launch leaves "approved" rows live.** The reject branch (`triggers.ts:385-387`) only transitions workflow state; distribution-created `approved` rows (`distribution-agent.ts:124,137`) are never reset. The fallback runner re-attempts them every minute; they fail closed at readiness but churn toward terminal `failed`.
- **(b) `brand_risk`-approved rows with `scheduledAt NULL` can stall.** `triggers.ts:401-407` flips status without scheduling; enqueue requires `workflowState ∈ {publication_pending, campaign_live}` **and** BullMQ (:413, :425-431). Otherwise nothing ever schedules them (`lte(scheduledAt, now)` never matches NULL).
- **(c) BullMQ-down "immediate" rows never execute.** `publishing-router.ts:75-99` creates `approved` rows with NULL `scheduledAt` and only enqueues when BullMQ is up; with BullMQ down no runner path matches.

## Recommendations (future slices, require product/governance authority)

1. Decide hold-then-settle vs keyed-deduction as the single billing authority, then either wire or delete the reservation engine (GAP18).
2. Converge calendar schedules onto the publishing queue, or document the calendar as display-only (GAP24).
3. Reset distribution-created queue rows when launch is rejected; schedule `brand_risk`-approved and immediate rows through a BullMQ-independent due path (GAP29 a–c).
4. Audit-log admin mutations; resolve the integration-token doc contradiction (GAP25).
