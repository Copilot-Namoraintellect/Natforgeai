# WBS-R3.2 — GAP24 Scheduling Convergence Report

**Branch:** `recovery/r3-integrity-closure`
**Status:** CLOSED (converged, with documented scope limits)

## Investigation findings

| Scheduling surface | Role | Verdict |
|---|---|---|
| `publishing_queue` → `publishSinglePost` | Sole executor of the "publish content post at time T" transition. BullMQ worker and the 60 s due-scan both funnel into it; `resolveExecutionDisposition` (publication-idempotency) is consulted before any provider call; `buildDuePostsCondition` due/not-due semantics are deterministic and documented (retrying rows with NULL `nextRetryAt` are BullMQ-only by design). | Already single authority — preserved unchanged. |
| `schedules` table (`api/schedule-router.ts`) | Calendar planning/display. Nothing outside the router reads or writes it. | Dead-end intake for campaign-linked content: `schedule.create` with a `contentPostId` enforced launch-approval readiness (`requireLaunchApproval: true`) and then persisted a row with **no execution path** — a governed gate consumed for an action that never happened. |
| Post-live observation scheduler (R1.5) | Separate workload, own Redis lease (`natforge:p1:post-live-metrics-observation`). | Intentionally separate — untouched. |
| Post-live lifecycle scheduler | Separate workload, own lease. | Intentionally separate — untouched. |

## Root cause

The calendar intake and the publishing queue were two authorities for one
transition. The evidence that the intake was *designed* to execute: the
`contentPostId`/`campaignId` columns, and the launch-approval readiness gate
in `schedule.create` — a gate only meaningful for a publication action. The
executor survived (WBS13); the bridge did not.

## Fix (narrowest compatible)

- New bridge `api/lib/publish/calendar-schedule-convergence.ts`:
  - resolves the declared calendar wall time through the existing WBS13.2
    `resolvePublicationSchedule` authority (IANA-zone, DST-safe, fail-closed,
    machine-local independent; not-before policy enforced; never ad-hoc date
    math);
  - inserts one durable `publishing_queue` row (status `approved` — the
    launch-approval gate already established authority; lowercase platform
    convention; `publishing_queue` remains the only execution authority);
  - schedules the existing BullMQ job when Redis is available, best-effort —
    with Redis down the approved row is picked up by the existing due-scan,
    so there is no BullMQ-down stall;
  - idempotent intake: the same user + content post + platform + canonical
    instant collapses onto the existing live row (`created: false` replay);
    terminally `failed` attempts are excluded so they can be re-intaken.
- `api/schedule-router.ts` `create`: campaign-linked content schedules route
  through the bridge after the existing gate; the `schedules` row is kept as
  the planning/calendar display record. One-off non-campaign posts stay
  planning-only (`publishing_queue.campaignId` is NOT NULL — the queue
  authority is campaign-scoped). Past instants fail closed before any row is
  written.
- `publishing-runner.ts` success path: mirrors `posted` onto same-user
  `schedules` rows for the published `contentPostId` (display convergence —
  one execution state never contradicted by a pending display state).
  Best-effort, post-commit, matching the surrounding refresh conventions.

## Outcome vs required semantics

- One clear authority per scheduled transition: `publishing_queue` executes;
  `schedules` is display/planning only.
- Deterministic due/not-due: canonical instant resolved once at intake by the
  WBS13.2 authority; due-scan semantics unchanged.
- No duplicate execution through competing schedulers: no new timer/lease
  introduced; BullMQ + due-scan continue to share the disposition-guarded
  single executor.
- Retry-safe: deterministic replay key at intake; deterministic BullMQ jobId
  (unchanged); execution idempotency unchanged.
- Lease/lock identities: post-live observation and lifecycle leases remain
  distinct (intentionally separate workloads).

## Documented scope limits (not invented)

- `schedule.update` does not retro-move queue rows: execution truth lives in
  the queue after intake (users manage queue rows via the publishing
  surfaces).
- Non-campaign one-off schedules remain planning-only records; the queue is
  campaign-scoped by schema.
- Terminal `failed` queue rows are not mirrored onto `schedules` (display
  lag remains possible on the failure direction; pre-existing behaviour, not
  a regression).
