## 1. Authority and evidence status

`F-CONTRACT` sections 2, 4-10 is the security authority for secret classes, reader identities, configuration source, redaction, break-glass separation and mandatory rotation after repository history exposure. Its R10-F acceptance is sibling-stream evidence, not proof that this frozen A baseline has the F implementation or OneGrid wiring. A04 defines proposed Windows identities/ACL scopes only. Source paths, commit heads and working-file SHA-256 references are catalogued in [A05 sources](r10-a-a05-sources.json); sibling Git cleanliness remains unverified as documented by A01.

Observed baseline behavior: `api/lib/env.ts` imports `dotenv/config`, reads required `APP_SECRET`, `DATABASE_URL` and `FIREBASE_SERVICE_ACCOUNT`, and requires `REDIS_URL` in production. Optional provider settings generally become empty strings. `api/lib/firebase-admin.ts` first parses `FIREBASE_SERVICE_ACCOUNT` as inline JSON, then treats it as a file path. This conflicts with F6's file-only Firebase service-account requirement. `api/lib/secrets.ts` is an optional Google Secret Manager helper for local scripts, not production runtime; it can fall back to ADC and writes fetched values into `process.env`. The existing PM2 preparation scripts read root `.env` and launch API/worker in the same operator environment. They are not approved Windows production injection or identity isolation. R10-F broker/redaction modules exist in the separate F source tree, not at the frozen A baseline; their presence does not establish enforcement in this deployment.

### F versus frozen-baseline gap

F's intended broker is closed-vocabulary and deny-by-default. Baseline A does not have the R10-F `api/lib/production-security/secret-broker.ts`, and `env.ts` directly reads `process.env`. Optional credentials silently become empty and some paths can fall back to other settings or development defaults; only the four required production settings fail at boot. Before production, owner-approved application work must bind each process to its approved reader set, remove inline Firebase JSON support, avoid overly broad environment inheritance, and make all enabled-feature dependencies fail closed. A05 does not implement or assign those code changes. Coordinate assignment and integrated acceptance through X; F owns classification/redaction semantics; implementer remains unresolved unless an authoritative assignment is recorded.

## 3. Windows injection and process boundaries

### Conditional injection design

The service supervisor has not been selected (D02). Therefore these are supervisor-independent security properties, not product instructions:

1. A trusted provisioning/secret authority creates a versioned, access-audited secret set outside Git, release directories, web roots, shared media, logs and backup payloads. Protect its local cache with A04's NatForgeAI-only inheritance boundary and explicit owner/DACL control.
2. At process start, a trusted supervisor-side injector resolves the approved version and supplies only that service identity's allowlisted variable names and file handles/paths. Prefer a supported OS credential vault or managed secret source when available. If unavailable, use a protected per-service configuration file outside releases, readable only by the relevant service identity and authorized administrator, plus an atomic protected update process. Do not place secrets in command-line arguments, wrapper XML, service `ImagePath`, IIS `web.config`, PM2 saved state, release manifests, interactive profile, machine-wide environment, or a shared `.env`.
3. API, worker and scheduler get separate process environments and separate credentials where their F reader sets differ. A process must not inherit the deployment agent's environment. Do not launch service children from the elevated Azure agent after it has loaded secrets. IIS app-pool identity serves static assets/proxies; it does not inject or govern the separately supervised Node process token.
4. Pass Firebase Admin a protected file path through `FIREBASE_SERVICE_ACCOUNT` only after application code is changed and verified to accept a path exclusively. Place the JSON file outside all release, web-served and backup staging trees; grant read to API identity only, no WRK/POOL/ND/MON/BKP access by default. Protect parent directories, owner and ACL; do not echo, parse-print, hash-print or copy file contents into reports. If a worker demonstrably imports Firebase Admin, resolve this against F's API-only reader contract before granting anything.
5. Backup encryption/offsite credentials are resolved only inside the isolated BKP job. Backup DB access must use a dedicated backup connection identity, not the application database URL; F/G/X must resolve a safe credential source that does not widen the F broker reader set. MON receives only required telemetry infrastructure credentials and cannot reuse Redis or provider credentials wholesale.
6. ND deployment authorization is distinct from secret-source administration. The existing `deployer` member of Administrators remains a privileged host residual; it must not receive runtime secrets by default. No production release may proceed on the assumption that a non-admin child neutralizes a privileged Azure agent parent. Select a constrained promotion/agent boundary and record its administrator risk acceptance first.
7. Rotation changes a secret version and process binding under a controlled window. Preserve independent stop state; never restart into a broader credential set, clear a stop latch, or use secret recovery as authority to enable providers/autonomy. Revocation must take effect at the source and old process tokens/sessions/connections must be drained or invalidated as designed.

Supervisor-specific details remain conditional: Windows service logon versus wrapper service account, secure file/handle delivery, environment-block update/restart semantics, secret refresh support, child-process inheritance, crash dump policy, service recovery actions and audit integration must be documented and tested for the selected supported product. Do not claim DPAPI, Credential Manager, gMSA, IIS configuration encryption or any vault is installed/available until verified. Environment variables are visible to sufficiently privileged local administrators and potentially diagnostic tooling; ACLs alone do not contain the existing administrator-privileged deployer.

## 4. Legacy exposure and rotation procedure

F-CONTRACT F9 reports that tracked `.env.production` and `.env.backup-*` files contained live-looking secrets in repository history; untracking alone does not remove historic exposure, so rotation is mandatory for affected classes. This specification intentionally does not inspect those values or identify individual credentials. Treat any credential that may have appeared in repository history, logs, release packages or broad admin-agent context as compromised until the security authority confirms rotation/revocation.

Required order, for each credential class and named provider:

1. Establish named owner, scope, target principal, dependencies, expiry/revocation method and rollback-safe overlap. Keep old and new values out of tickets, reports, command lines, screenshots and chat.
2. Issue replacement at the authoritative provider/DB/Redis/secret source with minimum scope. Verify permissions without printing material. For `APP_SECRET`, assess JWT/session invalidation and coordinated cutover; for `DATABASE_URL`, use a new least-privilege DB principal and prove access; for `REDIS_URL`, prove only required queue/store operations; for Firebase, rotate service-account key material and confirm API-only file delivery. For `TOKEN_ENCRYPTION_KEY`, do not rotate until versioning/re-encryption of persisted encrypted tokens is designed and rehearsed.
3. Bind replacement to one process role via the selected supervisor. Restart/drain safely; prove required readiness and no unintended effects. Never fall back to repository, `.env`, developer ADC, machine-wide credentials or a broader identity if resolution fails.
4. Revoke the prior credential at its issuer. Confirm old connections/tokens fail, new service remains healthy, audit events are attributable and no secret values appear in logs/telemetry/dumps.
5. Record only key name/class, opaque non-secret version ID, responsible authority, UTC timestamps, evidence references and result. Do not record value fingerprints that could enable offline guessing, secret-derived hashes or actual account identity data.

For overlapping provider/webhook rotations, preserve signature validation and reject ambiguous/unverified callbacks; coordinate provider-side old/new overlap only if the issuer supports a documented bounded window. Rotation does not grant activation approval, change default-deny gates, or authorize replay of uncertain external effects. F/R9-F/C/D/H authorities remain in force.

## 5. Failure and leakage behavior

| Condition | Required target behavior |
|---|---|
| Missing required secret, missing Firebase file, empty/truncated/malformed credential or unavailable source | Fail startup/readiness closed for the dependent process; do not use development defaults, inline fallback, alternate credentials with broader rights, ADC, local `.env`, or a different principal. Emit only bounded name/class/error code and release/process identity; never value/path if path sensitivity is not approved |
| Revoked credential / authorization denied | Stop dependent capability; fail requests/jobs explicitly and safely; no silent provider switch or redispatch with another identity. Preserve durable uncertainty and stop state; alert with redacted evidence |
| Stale/expired version | Reject where age/version policy requires; do not silently select `latest` unless the secret authority's version/rollback semantics are approved and auditable. Alert and require controlled rotation |
| Unauthorized identity/read | Deny before returning material; audit identity, class, variable name, process/release and correlation ID only. No retry using a privileged identity |
| Secret source outage | Existing processes may continue only for a bounded, documented lease/window with already-issued credentials if the selected mechanism safely supports that policy; otherwise fail closed. New process/restart cannot start without current valid material. Offline stale cache policy is unresolved and must not broaden authority |
| Secret detected in log, crash dump, telemetry, deployment artifact or frontend bundle | Treat as exposure: restrict access, preserve redacted evidence, revoke/rotate affected credential, audit and notify assigned F/security authority; remove leaked copy where approved. Do not paste finding into Codex output |

Logging and telemetry must redact recursively by secret names and shapes, including nested errors and environment snapshots. Crash dumps and process diagnostics may contain environment/file contents: disable or tightly ACL, encrypt and time-bound any required dump, exclude from backup/offsite upload unless explicitly protected, and purge under approved incident retention. Never capture an unredacted environment block. Secret scanning findings must be names/counts or salted-independent redacted location references, not payload excerpts or reversible hashes. Codex output and A05 artifacts contain names and design evidence only; no credential values, account identifiers, personal account data, tokens, connection strings, JSON bodies or value-derived hashes.

Git exclusion and build hygiene: filled local configuration files stay untracked; verify ignore rules and tracked-file/history scanners in the eventual release gate. `.env.example` may carry names and empty placeholders only, never usable values. Package allowlists must exclude `.env*` except approved example, Firebase key files, private keys, backup sets, credential caches, local ADC state, crash dumps, diagnostics and secret-source caches. Build-time `VITE_*` variables are public by design: bundle inspection must prove that only approved public Firebase client settings are present. Do not rely on Git ignore alone to prevent already-tracked/history exposure.

## 6. Independent boundaries and approvals

- **A04 ACLs:** create role-specific protected secret/config directories outside immutable releases and web roots. API-only Firebase file read; no broad BUILTIN\Users, IIS_IUSRS, ND, POOL, MON or WRK grant unless explicitly justified by an audited consumer. Protect parent ACL, owner, reparse/move paths and backup restore behavior. The actual inherited `D:\www` permissions are not known beyond the broad Users inheritance fact.
- **IIS and Node:** IIS pool identity has no Node secrets. API and worker are separately supervised tokens with separate bindings. A loopback proxy does not isolate local secrets or authenticate callers.
- **Azure DevOps:** current administrator-privileged `deployer` remains a privileged host boundary. Do not inject runtime secrets into its job environment or expose secret store read rights to its agent by default. A privileged parent can still replace files, service definitions or tokens; stronger promotion isolation and residual risk acceptance are D02/D05/D07 decisions.
- **Backup (G):** `BKP` alone receives backup encryption/offsite credentials. Runtime gets no backup secret or backup read/delete right. G's database dump needs a dedicated DB credential; its source and F classification are unresolved, and must not be solved by widening the F broker `DATABASE_SECRET` readers to BKP.
- **Monitoring (E):** collector gets only redacted projections/status and its own telemetry credential. E persistence/writer and independent human alert administration are not the same as MON. Monitoring outage must not cause the application to obtain alert-control or secret-admin authority.
- **Independent stop (H):** runtime cannot read STOP credentials, clear the latch, change stop configuration or upgrade itself. Credentials needed for incident administration remain external and independently authorized. Secret rotation/restart never resumes autonomy or clears suspension.
- **Provider/adapters (D/F):** only explicitly configured and approved providers receive scoped provider credentials. Empty/missing credential fails the specific capability; no mock/live fallback with broader authority. F's API/worker reader class and F's provider-adapter class need a concrete secret-source binding. `SCH` has no provider-secret entitlement in F2; provider-capable scheduler/recovery consumers remain blocked pending F/X decision.
